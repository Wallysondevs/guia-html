HTML Desempenho

Uma página rápida não depende só da internet do visitante: depende também da ordem em que o navegador descobre e baixa cada arquivo. Com algumas palavras no HTML, você pode dizer "este script pode esperar" (defer), "vou precisar desta imagem já" (preload), "o visitante provavelmente vai abrir esta página depois" (prefetch) e "esta foto é a mais importante" (fetchpriority). Nesta aula você vai ver, no console, a ordem real em que os scripts rodam, e aprender quando cada pedido ajuda e quando atrapalha.

Você vai aprender
  • Como o navegador lê a página e por que um <script> no <head> o faz parar.
  • defer e async: baixar o script sem travar a leitura.
  • <link rel="preload"> e o atributo as: baixar cedo o que o navegador só descobriria tarde.
  • <link rel="prefetch">: adiantar a próxima página.
  • preconnect e dns-prefetch: adiantar a conversa com outro site.
  • fetchpriority: dizer qual imagem é a mais importante.
  • Os erros reais do validador e os avisos do console do navegador.

As mensagens do validador desta aula saíram do validador W3C (vnu, o mesmo do validator.w3.org) na máquina da Ana (usuária ana, computador notebook), na pasta ~/site. A ordem dos scripts e os avisos do console foram conferidos no Chromium, servindo a página por http://, como num site de verdade. A aula anterior, Carregamento Preguiçoso, cuidou das imagens que podem esperar; esta cuida do que não pode.

A ideia: a lista de compras da festa

A Ana vai fazer uma festa. Ela pode ir ao mercado uma coisa por vez: lê a receita do bolo, descobre que falta farinha, vai ao mercado, volta, lê mais um pouco, descobre que falta chocolate, vai de novo. Ou pode ler tudo antes e mandar alguém buscar os ingredientes enquanto ela já começa a arrumar a casa.

O navegador enfrenta o mesmo problema. Ele lê o HTML de cima para baixo e, a cada arquivo que descobre (um CSS, um script, uma imagem), pede ao servidor. Os atributos desta aula são os recados que você deixa para ele: "este pode buscar depois", "este busque já", "este é o mais urgente".

1. O navegador lê de cima para baixo e para nos scripts

Quando o navegador encontra um <script src="…"> comum, ele para de ler o HTML, baixa o script, roda o script e só então continua. Ele faz isso porque o script pode mudar a página que vem depois. Enquanto isso, o visitante olha para uma tela em branco.

Esta página tem dois scripts no <head>: o normal.js, comum, e o adiado.js, com defer. Cada um pergunta se o <h1> já existe. Rode e leia a ordem no console:

<!DOCTYPE html>
<html lang="pt-BR">
<head>
<meta charset="utf-8">
<title>Receitas da Ana</title>
<script src="normal.js"></script>
<script src="adiado.js" defer></script>
</head>
<body>
<h1>Receitas da Ana</h1>
<script>
  console.log("2. script no fim do body");
  document.addEventListener("DOMContentLoaded", () => console.log("4. o HTML foi todo lido"));
</script>
</body>
</html>

console.log("1. normal.js: o h1 existe? " + (document.querySelector("h1") !== null));

console.log("3. adiado.js (defer): o h1 existe? " + (document.querySelector("h1") !== null));

O console mostra, nesta ordem:

1. normal.js: o h1 existe? false
2. script no fim do body
3. adiado.js (defer): o h1 existe? true
4. o HTML foi todo lido
  1. O normal.js rodou no meio do <head>, antes de o navegador ler o <h1>: para ele, o título ainda não existe.
  2. O navegador continuou lendo e rodou o script do fim do <body>.
  3. O adiado.js foi baixado enquanto o navegador lia, mas só rodou quando o HTML inteiro foi lido: o <h1> já existe.
  4. Logo depois, o navegador avisa que terminou de ler (o evento DOMContentLoaded, "conteúdo do DOM carregado").

O adiado.js foi escrito antes do script do fim do <body>, mas rodou depois: é o efeito do defer.

2. defer: baixe agora, rode no fim

<head>
  <meta charset="utf-8">
  <title>Receitas da Ana</title>
  <script src="menu.js" defer></script>
</head>
src="menu.js"
O arquivo do script (aula O Elemento script).
defer
"Adiar". Um atributo booleano: basta o nome. O navegador baixa o script em paralelo, sem parar de ler o HTML, e só o roda quando a página inteira foi lida. Vários scripts com defer rodam na ordem em que aparecem no HTML.

Com defer, você ganha duas coisas: a página aparece mais cedo (a leitura não para) e o script encontra todos os elementos (o problema do null, visto na aula canvas, some). Por isso o costume moderno é pôr os scripts no <head> com defer, em vez de no fim do <body>. O defer funciona em todos os navegadores há muitos anos.

3. async: rode assim que chegar

O async ("assíncrono") também baixa sem parar a leitura, mas roda o script assim que ele chega, no meio da leitura ou depois, sem esperar ninguém. Se a página tiver dois scripts async, o que chegar primeiro roda primeiro: a ordem pode mudar de uma visita para outra.

<script src> no <head>sim, enquanto baixa e rodana horaa do HTMLquase nunca
<script src> no fim do <body>não (já leu quase tudo)no fima do HTMLo jeito antigo; ainda funciona
<script src defer>nãoquando o HTML foi todo lidoa do HTMLos scripts da sua página
<script src async>não para baixar (só um instante, para rodar)assim que chegaqualquer umascripts independentes, como um contador de visitas
<script type="module" src>nãocomo o defer, sozinhoa do HTMLJavaScript moderno, com import

O defer e o async só funcionam com src: num script escrito direto na página, eles não fazem nada, e o validador acusa (veja em Quando dá errado).

4. preload: busque já, vou precisar logo

Alguns arquivos o navegador só descobre tarde: uma imagem de fundo escrita dentro do CSS, uma fonte de letra pedida pelo CSS. Ele precisa primeiro baixar e ler o CSS para saber que eles existem. O <link rel="preload"> ("pré-carregar") avisa já no <head>: "busque este arquivo agora, com prioridade, que ele vai ser usado nesta página":

<head>
  <meta charset="utf-8">
  <title>Receitas da Ana</title>
  <link rel="preload" href="assets/midia/bolo-1200.jpg" as="image">
  <link rel="preload" href="fontes/caderno.woff2" as="font" type="font/woff2" crossorigin>
  <link rel="stylesheet" href="estilo.css">
</head>
rel="preload"
A relação: "pré-carregue este arquivo". Não mostra nada na página: só antecipa o download. Quem usa o arquivo continua sendo o CSS (ou a <img>, ou o script).
href="…"
O arquivo. Tem de ser exatamente o mesmo endereço que a página vai usar depois; senão, o navegador baixa duas vezes.
as="image"
"Como": o tipo do arquivo. É obrigatório. Os mais comuns: image, font, style (CSS), script e fetch (dados). Com ele, o navegador sabe a prioridade certa e consegue reaproveitar o download.
type="font/woff2"
O formato da fonte. Um navegador que não entende o formato nem baixa.
crossorigin
As fontes são sempre pedidas num "modo especial" (o modo CORS), mesmo quando vêm do seu próprio site. O preload de uma fonte precisa pedir do mesmo jeito; sem o crossorigin, o pedido não combina, e a fonte é baixada duas vezes. O validador não avisa.
Preload demais atrapalha

Tudo o que tem preload passa na frente da fila. Se você pré-carrega dez coisas, nenhuma é especial, e o que importa de verdade (o CSS, a foto do topo) espera. Use para um ou dois arquivos que o navegador descobriria tarde. E se o arquivo pré-carregado não for usado, o Chrome reclama no console do F12, alguns segundos depois de a página carregar:

The resource http://localhost:8000/assets/midia/bolo-1200.jpg was preloaded using link preload but not used within a few seconds from the window's load event. Please make sure it has an appropriate `as` value and it is preloaded intentionally.

"O arquivo foi pré-carregado, mas não foi usado poucos segundos depois de a página carregar. Confira se o as está certo e se o pré-carregamento é de propósito." (A página de teste foi servida com python3 -m http.server, por isso o endereço começa com http://localhost:8000; veja a aula Servidor Local.)

O preload funciona em todos os navegadores atuais desde 2021, quando o Firefox, o último, passou a aceitar.

5. prefetch: adiantar a próxima página

O preload é para esta página. O prefetch ("buscar antes") é para a próxima: quando você tem quase certeza de para onde o visitante vai depois, pede ao navegador para baixar essa página com baixa prioridade, quando estiver à toa:

<link rel="prefetch" href="receita-bolo.html">

Se o visitante clicar no link da receita, ela abre mais rápido, porque já está guardada. Se não clicar, o download foi desperdiçado: por isso, use só quando o próximo passo é muito provável (a página 2 de uma lista, o passo 2 de um cadastro). Nem todo navegador atende esse pedido (o Safari, por muito tempo, ignorou o prefetch), mas, como é só um pedido, nada quebra.

preconnect e dns-prefetch: adiantar a conversa com outro site

Antes de baixar qualquer arquivo de outro site (as fontes do Google, um vídeo incorporado), o navegador precisa achar o endereço do site e abrir uma conexão segura com ele. Isso leva um tempinho. Dois pedidos adiantam essa parte:

<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link rel="dns-prefetch" href="https://videos.exemplo.com">
rel="preconnect"
"Pré-conectar": acha o endereço e abre a conexão. Use para um ou dois sites de que a página vai precisar logo.
rel="dns-prefetch"
Só acha o endereço (o DNS é a "lista telefônica" da internet, que troca o nome do site pelo número dele). Mais leve; serve para sites que talvez sejam usados.

6. fetchpriority: qual imagem é a mais importante

O navegador adivinha a prioridade de cada imagem, e às vezes erra: a foto grande do topo pode ficar na fila atrás de ícones pequenos. O atributo fetchpriority ("prioridade de busca") corrige o palpite:

<h1>Bolo de cenoura</h1>
<img src="assets/midia/bolo-800.jpg" alt="Bolo de cenoura com cobertura de chocolate"
     width="800" height="600" fetchpriority="high">

Na tela, nada muda: a foto é a mesma. A diferença está na fila de downloads, que você vê na aba de rede do F12 (numa página com várias imagens, a de high sai na frente).

ValorSignificado
highAlta: "esta é a foto principal, busque antes das outras"
lowBaixa: "esta pode esperar" (uma imagem de um carrossel que ainda não apareceu)
autoAutomático: o navegador decide (o padrão)

Ele vale em <img>, <link> (inclusive no preload) e <script>. Num <iframe>, o validador recusa: Attribute “fetchpriority” not allowed on element “iframe” at this point. É o contrário do loading="lazy", e os dois não combinam na mesma imagem. Todos os navegadores atuais entendem o fetchpriority desde o fim de 2024 (o Chrome desde 2022, o Safari desde o fim de 2023 e o Firefox por último); quem não entende, ignora.

Uma regra de ouro: meça antes de otimizar. No F12, a aba de rede mostra cada arquivo e quanto ele demorou, e a ferramenta Lighthouse do Chrome dá uma nota de desempenho com sugestões (aula Ferramentas do Desenvolvedor). Um pedido no lugar errado pode deixar a página mais lenta.

Quando dá errado

A “link” element with a “rel” attribute that contains the value “preload” must have an “as” attribute.

O que o navegador faz: sem o as, o pré-carregamento não serve para nada: o navegador não sabe o tipo do arquivo e não consegue reaproveitar o download.

<!DOCTYPE html>
<html lang="pt-BR">
<head>
<meta charset="utf-8">
<title>Receitas da Ana</title>
<link rel="preload" href="fonte.woff2">
</head>
<body>
<h1>Receitas da Ana</h1>
</body>
</html>

$ vnu index.html
"file:/home/ana/site/index.html":6.1-6.39: error: A “link” element with a “rel” attribute that contains the value “preload” must have an “as” attribute.

"Um link com rel="preload" precisa ter um atributo as." Com um valor que não existe, como as="fonte", saem dois erros para a mesma linha:

$ vnu index.html
"file:/home/ana/site/index.html":6.1-6.50: error: Bad value “fonte” for attribute “as” on element “link”.
"file:/home/ana/site/index.html":6.1-6.50: error: The value “fonte” is not a valid value for the “as” attribute of a “link” element with “rel=preload”.

Como consertar: o tipo em inglês: as="font", as="image", as="style", as="script".

An inline “script” element … must not have a “defer” attribute.

O que significa: <script defer>console.log(1)</script>, um script escrito direto na página, com defer. O navegador ignora o defer e roda o script na hora.

$ vnu index.html
"file:/home/ana/site/index.html":6.1-6.14: error: An inline “script” element (i.e., a “script” element without a “src” attribute and with a “type” attribute that is either unspecified, empty, or a JavaScript MIME type) must not have a “defer” attribute.

"Um script embutido (sem src) não pode ter defer." Como consertar: mova o código para um arquivo e use <script src="arquivo.js" defer>, ou deixe o script embutido no fim do <body>.

A “script” element with “type=module” must not have a “defer” attribute.

O que significa: um <script type="module" src="…" defer>. O módulo já espera a página ser lida sozinho; o defer é repetido. O navegador não se importa, mas o validador acusa (com o script na linha 7):

$ vnu index.html
"file:/home/ana/site/index.html":7.1-7.39: error: A “script” element with “type=module” must not have a “defer” attribute.

Como consertar: apague o defer. (O async num módulo é permitido e muda o comportamento: o módulo roda assim que chega.)

Bad value “false” for attribute “defer” on element “script”.

O que significa: defer="false". Como em todo atributo booleano, o que conta é ele existir: o navegador adia o script do mesmo jeito. O validador recusa o valor (linha 6):

$ vnu index.html
"file:/home/ana/site/index.html":6.1-6.33: error: Bad value “false” for attribute “defer” on element “script”.

Como consertar: para não adiar, apague o atributo.

Bad value “alta” for attribute “fetchpriority” on element “img”.

O que o navegador faz: ignora o valor e usa auto. A foto não ganha prioridade nenhuma, em silêncio.

$ vnu index.html
"file:/home/ana/site/index.html":8.1-8.77: error: Bad value “alta” for attribute “fetchpriority” on element “img”.

(Com <img src="bolo.jpg" alt="Bolo" width="800" height="600" fetchpriority="alta"> na linha 8.) Como consertar: high, low ou auto, em inglês.

O validador aceita, mas o navegador baixa duas vezes

O que acontece: o preload e o uso de verdade não combinam: o href é diferente (bolo-1200.jpg no preload e bolo-800.jpg no CSS), o as é de outro tipo, ou falta o crossorigin numa fonte. A página passa no validador sem erros, mas o navegador baixa o arquivo pré-carregado à toa e depois baixa o de verdade. O Chrome costuma avisar no console do F12, como no aviso da seção 4.

Como consertar: copie o endereço exatamente como ele aparece no CSS ou na <img>, confira o as e, para fontes, ponha crossorigin.

Resumo

  • O navegador lê o HTML de cima para baixo e para num <script src> comum até baixá-lo e rodá-lo.
  • defer: baixa sem parar e roda quando o HTML foi lido, na ordem. É o jeito recomendado para os scripts da página. async: roda assim que chega, em qualquer ordem. type="module" já é adiado. Os três só valem com src.
  • <link rel="preload" href as> busca já um arquivo desta página que seria descoberto tarde; o as é obrigatório, e fontes precisam de crossorigin. Preload demais atrapalha.
  • prefetch adianta a próxima página; preconnect e dns-prefetch adiantam a conversa com outro site.
  • fetchpriority="high" na foto principal; loading="lazy" nas de baixo.
  • Valores errados (as="fonte", fetchpriority="alta", defer="false") o validador pega; o href diferente entre o preload e o uso, não. Meça no F12 antes e depois.
