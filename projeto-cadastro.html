Projeto Formulário de Cadastro

A lojinha de doces da Ana cresceu, e ela quer uma lista de clientes: para avisar das novidades e para ter o endereço de entrega de cada um. Neste projeto você monta o formulário de cadastro completo: cada campo com o seu nome, o tipo certo de campo para cada informação, grupos que organizam a página e a conferência dos dados antes de enviar. E tudo acessível: quem usa leitor de tela, só o teclado ou o celular consegue se cadastrar sem adivinhar nada.

Você vai praticar
  • Montar um formulário com form, input e button (Formulários, input, Botões).
  • Ligar cada campo ao seu nome com label, for e id (label).
  • Escolher o tipo certo: email, tel, date, password (Tipos de input) e o autocomplete (placeholder, value, autocomplete…).
  • Usar select, radio, checkbox e textarea (select, checkbox e radio, textarea).
  • Agrupar com fieldset e legend (fieldset).
  • Conferir os dados com required, minlength e pattern, com dicas que o leitor de tela também lê (Validação, Formulários Acessíveis).

O que vamos construir

O formulário pronto, desenhado pelo seu navegador. Ele funciona: clique em Cadastrar sem preencher nada e veja o navegador parar no primeiro campo obrigatório. Depois preencha tudo e clique de novo. Num site publicado, os dados iriam para o servidor da lojinha; o editor do guia não tem servidor, então mostra uma página "Formulário enviado" com o que seria enviado.

Antes de começar

Você precisa ter visto Formulários, label e Tipos de input; para as versões 3 e 4, checkbox e radio, fieldset e Validação. A pasta do projeto:

$ mkdir -p sites/cadastro
$ cd sites/cadastro

Versão 1 · O formulário mínimo

Pense numa ficha de papel na loja: cada linha tem um rótulo impresso ("Nome:") e um espaço para escrever. No HTML, o rótulo é o label, o espaço é o input, e a ficha inteira é o form. Começamos com dois campos e o botão.

<!DOCTYPE html>
<html lang="pt-BR">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Cadastro — Doces da Ana</title>
</head>
<body>
  <h1>Cadastro de clientes</h1>
  <p>Cadastre-se para receber as novidades da lojinha.</p>

  <form action="https://example.com/cadastro" method="post">
    <p>
      <label for="nome">Nome completo</label>
      <input type="text" id="nome" name="nome">
    </p>
    <p>
      <label for="email">E-mail</label>
      <input type="email" id="email" name="email">
    </p>
    <p>
      <button type="submit">Cadastrar</button>
    </p>
  </form>
</body>
</html>
<form action="…" method="post">
O formulário. action é o endereço do programa que recebe os dados no servidor (aqui, um endereço de exemplo); method="post" manda os dados no corpo da mensagem, e não no endereço, como se deve fazer com dados pessoais (veja Enviar: GET e POST).
<label for="nome">
O rótulo. O for diz de qual campo ele é: o campo com id="nome".
<input type="text" id="nome" name="nome">
O campo. O id é o "RG" do campo dentro da página (o label usa). O name é o nome com que o dado é enviado (o servidor usa). Podem ser iguais, e quase sempre são.
type="email"
Um campo de e-mail: o celular mostra um teclado com @, e o navegador confere se parece um e-mail antes de enviar.
<button type="submit">
O botão que envia o formulário.
<p> … </p>
Cada par rótulo + campo num parágrafo, para cada um ficar na sua linha (label e input ficam lado a lado; veja Bloco × Em Linha).

O label ligado ao campo faz duas coisas. Clique na palavra "Nome completo" no resultado acima: o cursor vai para o campo, e a área de clique fica maior (no celular, isso ajuda muito). E o leitor de tela, ao entrar no campo, lê "Nome completo": a pessoa sabe o que digitar.

O for não bate com o id

A Ana digitou <label for="nomes">, mas o campo é id="nome". Na tela, tudo igual. Mas clicar no rótulo não faz mais nada, e o leitor de tela anuncia só "editar texto", sem dizer qual. O validador acusa:

$ vnu --verbose index.html
index.html
"file:/home/ana/sites/cadastro/index.html":14.7-14.25: error: The value of the “for” attribute of the “label” element must be the ID of a non-hidden form control.

"O valor do atributo for do label tem de ser o id de um campo de formulário visível." Como consertar: o for e o id escritos exatamente iguais (maiúsculas contam).

Versão 2 · O tipo certo para cada dado

Num formulário de papel, a data de nascimento tem quadradinhos para dia, mês e ano. No HTML, o type faz esse papel: diz ao navegador que tipo de dado vai ali, e ele ajuda a pessoa (teclado certo no celular, calendário, senha escondida). E o autocomplete diz ao navegador qual dado é, para ele oferecer o que a pessoa já digitou em outros sites.

CampotypeO que o navegador fazautocomplete
NometextUma linha de texto comum.name (nome completo)
E-mailemailTeclado com @ no celular; confere o formato antes de enviar.email
CelulartelTeclado de telefone no celular. Não confere o formato (cada país escreve de um jeito).tel
NascimentodateUm seletor de data (o desenho muda de navegador para navegador). O valor enviado é sempre ano-mês-dia, como 1995-03-21.bday (birthday, aniversário)
SenhapasswordMostra bolinhas no lugar das letras.new-password: "senha nova"; o navegador pode sugerir uma senha forte.
CEPtext + inputmode="numeric"Teclado de números no celular, mas o campo continua sendo texto.postal-code
EstadoselectUma lista de opções que abre e fecha.address-level1 (estado)
<select id="estado" name="estado">
A caixa de escolha. Leva id, name e um label, como os outros campos.
<option value="">Escolha…</option>
A primeira opção, vazia, convida a escolher. Sem ela, "São Paulo" já viria marcado, e quem não mexer seria cadastrado em São Paulo sem perceber.
<option value="SP">São Paulo</option>
O texto aparece para a pessoa; o value é o que vai para o servidor. Num site de verdade, liste os 27 estados.
Por que o CEP não é type="number"?

Porque CEP não é número de fazer conta: ninguém soma CEPs. Com type="number", o campo ganha setinhas para aumentar e diminuir o valor, e o traço de "01234-567" não é aceito. O mesmo vale para telefone, CPF e número de cartão. Use type="number" para quantidades e idades; para códigos, text com inputmode="numeric".

<fieldset>
Um grupo de campos. O navegador desenha uma moldura em volta.
<legend>
O título do grupo, encaixado na moldura. Tem de ser o primeiro filho do fieldset. O leitor de tela lê a legenda ao entrar no grupo.
<input type="radio" name="contato" value="email" checked>
Uma opção de "escolha uma". Todas as opções da mesma pergunta têm o mesmo name: é isso que faz marcar uma desmarcar a outra. O value é o que vai para o servidor (contato=email). checked deixa esta marcada no começo.
<label for="por-email">
Cada opção tem o seu rótulo, depois da bolinha (é o costume para radio e checkbox). Clicar no texto marca a opção.
<input type="checkbox" name="interesse">
"Marque quantas quiser". Se a pessoa marcar duas, vão duas: interesse=bolos&interesse=doces.
<textarea rows="3" cols="40"></textarea>
Um campo de várias linhas: 3 linhas de altura e cerca de 40 letras de largura. Repare que ele tem tag de fechamento, e que nada pode ficar entre as duas tags (nem um espaço), senão o espaço vira o texto inicial do campo.

A pergunta "Como prefere receber as novidades?" é a legend de um fieldset dentro do grupo Preferências. Assim, quando o leitor de tela chega à opção "Não quero receber", ele lê também a pergunta. Sem isso, a pessoa ouviria só "Não quero receber, botão de opção" e teria de adivinhar o quê.

AtributoOndeO que o navegador confere
requirednome, e-mail, senha, CEP e o aceiteQue o campo não está vazio (no checkbox, que está marcado). O leitor de tela também anuncia "obrigatório".
minlength="8"senhaQue tem pelo menos 8 caracteres.
pattern="[0-9]{5}-?[0-9]{3}"CEPQue o valor inteiro segue o molde: 5 dígitos, um traço opcional e 3 dígitos.
type="email"e-mailQue parece um e-mail (algo, @, algo).
[0-9]{5}
Um dígito de 0 a 9 ([0-9]), cinco vezes ({5}).
-?
Um traço, que pode aparecer ou não (o ? quer dizer "opcional").
[0-9]{3}
Mais três dígitos. Passam 01234-567 e 01234567; não passam 01234 567 (com espaço) nem 1234-567 (faltou um dígito).
aria-describedby="dica-cep"
Liga o campo à dica com id="dica-cep". O leitor de tela lê o rótulo e, logo depois, a dica: "CEP, obrigatório, 8 números, com ou sem traço…" (veja ARIA).
<small id="dica-cep">
A dica, visível para todos, logo depois do campo.
(obrigatório)
Escrito no rótulo. Um asterisco sozinho não diz nada a quem nunca viu essa convenção; a palavra diz.

Experimente no resultado acima: clique em Cadastrar sem preencher nada. O navegador não envia; ele leva o cursor até o primeiro campo com problema (o nome) e mostra um balão com o motivo. O texto do balão é do próprio navegador, no idioma dele. Depois escreva 01234 567 no CEP e tente de novo: o balão agora reclama do formato. Só quando tudo estiver certo aparece a página "Formulário enviado".

A conferência do navegador ajuda a pessoa, mas não protege a loja

Qualquer pessoa pode desligar essas conferências ou mandar dados direto para o servidor, sem passar pela página. Por isso o programa que recebe o cadastro tem de conferir tudo de novo. A validação do HTML existe para a pessoa descobrir o erro na hora, sem esperar a resposta do servidor (veja Segurança).

Só o placeholder, sem label

Uma moda comum é tirar o rótulo e deixar só o texto cinza dentro do campo (o placeholder). Fica "limpo", e o validador aceita. Experimente escrever no campo do nome:

<!DOCTYPE html>

    <p><input type="text" name="nome" placeholder="Nome completo"></p>
    <p><input type="email" name="email" placeholder="E-mail"></p>
    <p><button type="submit">Cadastrar</button></p>
  </form>
</body>
</html>

O que acontece: o texto cinza some assim que você começa a digitar. Quem se distrai no meio não sabe mais que campo era aquele, e quem tem dificuldade de memória precisa apagar para ver. O cinza claro também é difícil de ler para muita gente. Como consertar: sempre um label; o placeholder, se houver, é só um exemplo a mais (veja Formulários Acessíveis).

Missão (versão 4): os rótulos já dizem "(obrigatório)", mas o navegador ainda não sabe disso. Coloque required no nome, no e-mail, na senha, no CEP e no checkbox do aceite; na senha, acrescente minlength="8"; no CEP, pattern="[0-9]{5}-?[0-9]{3}". Depois, tente cadastrar com o formulário vazio.

Conferindo a acessibilidade

Uma lista rápida para qualquer formulário, que esta versão final cumpre:

  1. Todo campo tem um label visível, ligado por for e id.
  2. Opções de uma mesma pergunta ficam num fieldset com a pergunta na legend.
  3. O que é obrigatório está escrito na tela e marcado com required.
  4. As regras (tamanho da senha, formato do CEP) aparecem antes do erro, e estão ligadas ao campo com aria-describedby.
  5. Dá para preencher e enviar só com o teclado: Tab passa de campo em campo, as setas trocam a opção do radio, Espaço marca o checkbox e Enter envia (veja Teclado e Foco). Teste você mesmo no resultado.

Desafios extras

  1. Sugestões de cidade. Use um <datalist> para sugerir as cidades em que a Ana entrega (veja datalist).
  2. Grupos de estados. Separe as opções do select por região com <optgroup label="Sudeste"> (veja select).
  3. Limite no texto. Ponha maxlength="300" no textarea e escreva a regra numa dica ligada com aria-describedby.
  4. Um botão de limpar. Acrescente <button type="reset">Limpar</button> e pense: vale a pena? Muita gente clica nele sem querer e perde tudo (veja Botões).
  5. Busca de produtos. Faça um segundo formulário, de busca, com method="get", um <input type="search" name="q"> e um label. Envie e compare o endereço que o editor mostra com o do POST (veja Enviar: GET e POST).

Exercícios

1. Qual atributo liga um label ao seu campo?

2. Um campo foi preenchido, mas o dado não chegou ao servidor. O que provavelmente falta nele?

3. As três opções de um radio deixam marcar todas ao mesmo tempo. Qual é o erro?

4. Com pattern="[0-9]{5}-?[0-9]{3}", qual CEP o navegador aceita?

5. Por que a validação do navegador não basta para proteger a loja?

6. Complete o campo de e-mail, para o celular mostrar o teclado com @:

<input type="" id="email" name="email">

7. Complete o título do grupo de campos:

<fieldset> <>Endereço de entrega</legend> …

Resumo

  • Todo campo tem um label ligado por for = id; o name é o nome com que o dado é enviado, e campo sem name não vai.
  • O type certo ajuda a pessoa (teclado, calendário, senha escondida); o autocomplete deixa o navegador preencher sozinho.
  • Códigos como CEP e telefone são texto: inputmode="numeric", e não type="number".
  • fieldset e legend agrupam campos e dão a pergunta das opções; todas as opções de um radio têm o mesmo name.
  • required, minlength e pattern fazem o navegador conferir antes de enviar; as regras ficam escritas na tela e ligadas com aria-describedby.
  • A conferência do navegador ajuda a pessoa; o servidor confere de novo.
