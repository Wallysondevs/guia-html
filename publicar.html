HTML Publicar no GitHub Pages

Até agora, o site da Ana só existia no computador dela. Publicar é colocá-lo num servidor ligado na internet o dia inteiro, com um endereço que qualquer pessoa pode abrir. Existem muitos serviços para isso; nesta aula você vai usar o GitHub Pages, que publica sites de HTML, CSS e JavaScript de graça. Você vai ver dois caminhos: pelo site do GitHub, só com cliques, e pelo git, no terminal, que é como os profissionais trabalham.

Você vai aprender
  • O que conferir na pasta antes de publicar.
  • O que são o GitHub, um repositório e o GitHub Pages.
  • A publicar pelo site do GitHub: criar o repositório, enviar os arquivos e ligar o Pages.
  • O mesmo trabalho pelo git: git init, git add, git commit e git remote, com as saídas reais.
  • Qual é o endereço do site e por que ele tem o nome do repositório no fim.
  • A atualizar o site e a resolver os erros mais comuns.

Os comandos desta aula rodaram na máquina fictícia da Ana (usuária ana, computador notebook, Ubuntu 26.04), com o git 2.53.0 do Ubuntu, na pasta do site de receitas das aulas Organizar os Arquivos e Servidor Local. O último passo, o envio para o GitHub (git push), é descrito, mas não aparece rodando: ele precisa de uma conta e de uma senha especial, e cada leitor vai usar a sua. Onde aparecer SEU-USUARIO, troque pelo seu nome de usuário no GitHub.

A ideia: a vitrine da loja

A Ana faz bolos em casa. Para vender, ela precisa de uma vitrine numa rua movimentada. O GitHub é um prédio cheio de depósitos (os repositórios), um para cada projeto. O GitHub Pages é a vitrine: ele pega o que está num depósito e expõe na rua, com um endereço.

Pense no git como um álbum de fotos da pasta: cada vez que você "tira uma foto" (um commit), ele guarda como todos os arquivos estavam naquele momento. O GitHub guarda uma cópia desse álbum na internet, e o Pages mostra a foto mais recente como site.

1. Antes de publicar: a lista de conferência

O GitHub Pages é um servidor como o da aula Servidor Local, rodando em Linux. Tudo o que quebra num servidor quebra lá. Confira:

  1. A página inicial se chama index.html, em minúsculas, na raiz da pasta.
  2. Nomes de arquivo em minúsculas, sem espaços nem acentos: o servidor diferencia Foto.jpg de foto.jpg.
  3. Caminhos relativos: css/estilo.css e ../img/pudim.jpg. Nada de C:\…, de file:///, nem de caminho começando com / (seção 5 explica por quê).
  4. O HTML valida: vnu --skip-non-html . na pasta.
  5. Testou num servidor local e o registro não mostrou nenhum 404.
  6. Nada secreto na pasta: o site será público, e os arquivos do repositório também. Nada de senhas, planilhas pessoais, documentos.

Na pasta da Ana, o validador não disse nada, que é o que se espera:

$ vnu --skip-non-html --errors-only . ; echo "saida=$?"
saida=0

--errors-only mostra só os erros, e o código de saída 0 confirma: nenhum.

Missão: o editor que a Ana usava escreveu caminhos com a pasta do computador dela. No computador da Ana funciona; publicado, nenhum visitante tem um C:\Users\Ana. 2. Criar a conta e o repositório

A interface do GitHub é em inglês, e os nomes e a posição dos botões mudam de tempos em tempos. Os passos abaixo dizem o que procurar; se um botão estiver em outro lugar, procure pela mesma palavra.

  1. Crie uma conta grátis em github.com (botão Sign up, "cadastrar-se"). O nome de usuário que você escolher vai aparecer no endereço do site: https://SEU-USUARIO.github.io/. Escolha um que você não tenha vergonha de mostrar.
  2. Já logado, procure o botão + no alto da página e escolha New repository ("novo repositório").
  3. Em Repository name ("nome do repositório"), escreva receitas. As mesmas regras dos nomes de arquivo valem aqui: minúsculas e hífen. Esse nome vai virar parte do endereço.
  4. Deixe o repositório como Public ("público"). Na conta grátis, o GitHub Pages só funciona com repositórios públicos.
  5. Clique no botão de criar (Create repository). O repositório nasce vazio.

3. Caminho A: enviar os arquivos pelo site

O jeito mais simples, sem instalar nada:

  1. Na página do repositório vazio, procure o link uploading an existing file ("enviar um arquivo existente"). Num repositório que já tem arquivos, o mesmo fica no botão Add file → Upload files.
  2. Abra a pasta do site no seu computador, selecione o que está dentro dela (o index.html, o sobre.html e as pastas css, js, img, receitas) e arraste para a área indicada na página. Não arraste a pasta receitas de fora, a que contém tudo: o index.html precisa ficar na raiz do repositório, e não dentro de uma pasta.
  3. Embaixo, no campo da mensagem, escreva o que mudou, como "Primeira versão do site", e clique em Commit changes ("registrar as mudanças"). Isso é um commit: uma "foto" dos arquivos.
  4. Confira a lista de arquivos do repositório: o index.html deve aparecer ali, ao lado das pastas.
Arrastar pastas

Os navegadores atuais deixam arrastar pastas inteiras para a página de envio, e o GitHub recria as subpastas. Se o seu não deixar, envie as pastas uma de cada vez, ou use o caminho B.

4. Ligar o GitHub Pages

Os arquivos estão no depósito. Falta abrir a vitrine:

  1. No repositório, abra a aba Settings ("configurações").
  2. No menu da esquerda, clique em Pages.
  3. Em Build and deployment ("construção e publicação"), na opção Source ("origem"), escolha Deploy from a branch ("publicar a partir de um ramo").
  4. Em Branch, escolha main e a pasta / (root) (a raiz), e clique em Save ("salvar").
  5. Espere um ou dois minutos e recarregue a página de configurações. Quando o site estiver no ar, aparece no alto o endereço dele, com um botão para visitá-lo.
branch (ramo)
Uma linha de versões dentro do repositório. Todo repositório começa com um ramo, hoje quase sempre chamado main ("principal").
/ (root)
"Publique a partir da raiz do repositório". A outra opção, /docs, é para quem guarda o site numa pasta docs, ao lado de outros arquivos do projeto.

Na aba Actions do repositório, você vê o GitHub trabalhando: cada publicação aparece como uma tarefa, com um ícone que fica verde quando termina. Se ficar vermelho, clique para ver o motivo.

5. O endereço do site

O endereço de um repositório comum segue sempre a mesma forma:

https://SEU-USUARIO.github.io/receitas/
https://
Com cadeado: o GitHub Pages usa conexão segura sozinho, sem você configurar nada.
SEU-USUARIO.github.io
O "terreno" da sua conta no GitHub Pages. O GitHub escreve o nome de usuário em minúsculas nesse endereço.
/receitas/
O nome do repositório, como se fosse uma pasta. O index.html da raiz do repositório aparece aqui.

Esse /receitas/ explica o item 3 da lista de conferência. No site publicado, a raiz do servidor é https://SEU-USUARIO.github.io/, e o site da Ana mora uma pasta abaixo. Um caminho com barra no começo vai para a raiz do servidor, fora do site:

Na página https://SEU-USUARIO.github.io/receitas/index.htmlo navegador pederesultado
href="css/estilo.css"https://SEU-USUARIO.github.io/receitas/css/estilo.cssacha
href="/css/estilo.css"https://SEU-USUARIO.github.io/css/estilo.css404: o CSS some
Um site sem o nome do repositório no endereço

Se você der ao repositório o nome exato SEU-USUARIO.github.io, ele vira o seu site pessoal, publicado direto em https://SEU-USUARIO.github.io/, sem pasta no fim. Cada conta tem um só desse tipo. E, se você comprar um domínio próprio (como receitasdaana.com.br), dá para apontá-lo para o GitHub Pages na mesma tela de configurações, no campo Custom domain ("domínio personalizado").

6. Caminho B: o git, no terminal

Enviar pelo site é ótimo para começar, mas a cada mudança você teria de arrastar os arquivos de novo. Com o git, você registra as mudanças no seu computador e manda tudo com um comando. Primeiro, instale: no Ubuntu, sudo apt install git; no Windows e no macOS, há instaladores em git-scm.com. Confira:

$ git --version
git version 2.53.0
Português e inglês misturados

O git do Ubuntu fala português quando o sistema está em português, mas a tradução não está completa: as mensagens mais novas aparecem em inglês. As saídas abaixo são exatamente o que ele mostrou na máquina da Ana, mistura e tudo.

6.1 git init: começar o álbum

$ git init -b main
Repositório vazio Git inicializado em  /home/ana/sites/receitas/.git/
git init
"Inicie": transforma a pasta atual num repositório. Faça isso uma vez só, na raiz do site.
-b main
Já cria o ramo com o nome main, o mesmo que o GitHub usa. Sem o -b main, o git 2.53 cria um ramo chamado master e mostra um aviso longo (em inglês) sugerindo trocar.
.git/
Uma pasta escondida (o ponto no começo do nome a esconde) onde o git guarda o álbum inteiro. Não mexa nela; apagá-la apaga o histórico.

6.2 git status: o que o git está vendo

$ git status
No ramo main

No commits yet

Arquivos não monitorados:
  (utilize "git add <arquivo>..." para incluir o que será submetido)
	css/
	img/
	index.html
	js/
	receitas/
	sobre.html

nada adicionado ao envio mas arquivos não registrados estão presentes (use "git add" to registrar)

"Nenhum commit ainda" e seis itens "não monitorados": o git vê os arquivos, mas ainda não cuida deles. O git status é o comando que você mais vai usar: na dúvida, rode-o.

6.3 git add: escolher o que entra na foto

$ git add .
$ git status
No ramo main

O . quer dizer "tudo nesta pasta". Agora os nove arquivos estão na lista de "mudanças a serem submetidas", marcados como new file ("arquivo novo"). Ainda não há foto: o add só arruma quem vai aparecer nela.

6.4 git commit: tirar a foto

Na primeira vez, o git não sabe quem você é:

$ git commit -m "Primeira versão do site de receitas"
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'ana@notebook.(none)')

"Identidade do autor desconhecida. Por favor, diga quem você é." Todo commit leva o nome e o e-mail de quem o fez. O git até sugere os comandos. A Ana se apresentou (faça isso uma vez por computador) e tentou de novo:

$ git config --global user.name "Ana"
$ git config --global user.email "ana@example.com"
$ git commit -m "Primeira versão do site de receitas"
[main (root-commit) 9c3e761] Primeira versão do site de receitas
 9 files changed, 64 insertions(+)

A mensagem do commit: o que mudou, em poucas palavras. Ela aparece no histórico e no GitHub.

No ramo main, o primeiro commit de todos (root-commit, "commit raiz"). O 9c3e761 é o começo do código que identifica esta foto; o seu será outro.

"9 arquivos mudaram, 64 linhas acrescentadas".

Cada arquivo criado. O 100644 é o tipo de permissão de um arquivo comum; pode ignorar.

Use no user.email o mesmo e-mail da sua conta do GitHub (ou o e-mail "privado" que o GitHub oferece nas configurações da conta, se não quiser mostrar o seu): é assim que o GitHub liga os commits ao seu perfil. E lembre que o nome e o e-mail ficam públicos no histórico do repositório.

6.7 Ligar ao GitHub e enviar

Crie o repositório no GitHub como na seção 2, mas vazio (sem enviar arquivos nem criar README). Depois, diga ao git onde ele fica:

$ git remote add origin https://github.com/SEU-USUARIO/receitas.git
$ git remote -v
origin	https://github.com/SEU-USUARIO/receitas.git (fetch)
origin	https://github.com/SEU-USUARIO/receitas.git (push)
git remote add origin …
"Acrescente um repositório remoto chamado origin" ("origem", o nome de costume) com este endereço. O endereço aparece na página do repositório vazio, no GitHub.
(fetch) / (push)
O mesmo endereço serve para trazer (fetch) e para enviar (push, "empurrar").

O envio é o comando git push -u origin main ("empurre o ramo main para o origin"; o -u faz o git lembrar disso, e nas próximas vezes basta git push). Ele não aparece rodando aqui porque precisa da sua conta. O que você precisa saber:

  • O GitHub não aceita a senha da conta no git push. No lugar dela, ele pede uma "senha de aplicativo", o token de acesso pessoal (personal access token), criado nas configurações de desenvolvedor da conta. Outras saídas: o programa GitHub CLI (comando gh auth login), o Git Credential Manager (que vem com o git no Windows e abre uma janela de login) ou uma chave SSH.
  • Um token é como uma senha: nunca o coloque num arquivo do site, num print ou numa mensagem. Quem tem o token pode mexer nos seus repositórios.
  • Depois do primeiro push, ligue o GitHub Pages como na seção 4.

7. Atualizar o site

O site publicado sempre mostra a última versão do ramo main. Para mudar o site:

  • Pelo site do GitHub: envie de novo os arquivos mudados (Add file → Upload files; os de mesmo nome são substituídos) ou abra um arquivo e clique no ícone de lápis para editar ali mesmo. Cada envio termina com Commit changes.
  • Pelo git: o ciclo da seção 6.6 e, no fim, git push.

Em poucos minutos, o Pages publica a versão nova (acompanhe na aba Actions). Se o navegador continuar mostrando a antiga, recarregue ignorando a memória dele com Ctrl+Shift+R.

Quando dá errado

O endereço mostra "404" do GitHub

O que significa: o GitHub Pages não achou o que entregar. Causas, da mais comum para a menos: o Pages ainda está publicando (espere alguns minutos e veja a aba Actions); o index.html não está na raiz (ficou dentro de uma pasta, porque você arrastou a pasta de fora); o arquivo se chama Index.html ou index.htm; o Pages não foi ligado (seção 4); ou o endereço está com o nome do repositório errado.

Como consertar: abra o repositório e confira se o index.html aparece na primeira lista de arquivos, com esse nome exato.

O site abre, mas sem estilo (ou sem imagens)

O que significa: o HTML chegou, o CSS não. Quase sempre é um caminho: começa com / (vai para fora do /receitas/, seção 5), aponta para o seu computador (C:\, file:///), ou tem uma maiúscula diferente do nome do arquivo.

Como consertar: use caminhos relativos e nomes em minúsculas. O F12, na aba de rede, mostra em vermelho o endereço que deu 404 (aula Ferramentas do Desenvolvedor).

fatal: unable to auto-detect email address

O que significa: "não foi possível descobrir o endereço de e-mail sozinho". O commit precisa de um autor.

Como consertar: git config --global user.name "Seu Nome" e git config --global user.email "seu@email", e repita o commit.

fatal: not a git repository (or any of the parent directories): .git

O que significa: "não é um repositório git (nem nenhuma das pastas acima)": você rodou um comando do git fora da pasta do site (ou esqueceu o git init).

Como consertar: entre na pasta com cd ~/sites/receitas. Confira com ls -a se a pasta .git está lá.

O git push pede usuário e senha, e a senha é recusada

O que significa: o GitHub não aceita a senha da conta para o git (desde 2021).

Como consertar: use um token de acesso pessoal no lugar da senha, ou faça o login com gh auth login ou com o Git Credential Manager (seção 6.7).

Uma pasta que começa com _ não aparece no site

O que significa: por padrão, o GitHub Pages passa os arquivos por um programa chamado Jekyll, que ignora pastas e arquivos cujo nome começa com _ (como _imagens/).

Como consertar: renomeie a pasta (mais uma razão para seguir as regras de nomes), ou crie na raiz do repositório um arquivo vazio chamado .nojekyll, que desliga o Jekyll.
