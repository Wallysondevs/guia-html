A ideia: o catálogo e a embalagem

O computador não guarda letras: guarda bytes, números de 0 a 255. Para transformar letras em números, e de volta, existem duas peças:

  • Unicode é um catálogo: uma lista enorme, com mais de 150 mil caracteres, em que cada um tem um número fixo. O A é o 65, o ç é o 231, o € é o 8364, o 🎂 é o 127874. Esse é o número que você usou nas referências numéricas da aula Entidades (&#127874;).
  • UTF-8 é a embalagem: a regra que diz como guardar esses números em bytes. Número pequeno vai numa caixa de 1 byte; número maior, em 2, 3 ou 4 bytes.

Pense numa mudança: o catálogo diz o que é cada objeto; a embalagem decide quantas caixas ele ocupa no caminhão. Quem desembala precisa saber como as coisas foram embaladas. Se a Ana embalou em UTF-8 e a vizinha desembala achando que é outro sistema, as coisas saem trocadas.

Hoje, quase toda página da web (bem mais de 90%) usa UTF-8, e o HTML atual exige UTF-8 em páginas novas.

1. A linha que avisa: <meta charset="utf-8">

O arquivo HTML é uma fileira de bytes. Para o navegador saber que embalagem você usou, a página avisa logo no começo:

<!DOCTYPE html>
<html lang="pt-BR">
<head>
<meta charset="utf-8">
<title>Receitas da Ana</title>
</head>
<body>
<h1>Pão de queijo</h1>
<p>Ação rápida: 30 minutos de forno.</p>
</body>
</html>
<meta>
Um elemento de "informação sobre a página" (aula title e meta). Não aparece na tela e não tem tag de fechamento.
charset
De character set, "conjunto de caracteres". Na prática, diz qual codificação (embalagem) o arquivo usa.
"utf-8"
O único valor permitido hoje. Maiúsculas ou minúsculas tanto faz (UTF-8 também vale), mas o hífen é obrigatório (veja Quando dá errado).
logo depois do <head>
O navegador procura essa linha nos primeiros 1024 bytes do arquivo. Colocada como primeira coisa do head, antes do <title> (que já tem letras acentuadas em muitos sites), ela chega a tempo.

O meta charset é um aviso, e não uma conversão: ele diz "estes bytes são UTF-8". Para o aviso ser verdade, o arquivo também precisa estar salvo em UTF-8. Todo editor moderno, como o VS Code, salva em UTF-8 por padrão e mostra a codificação na barra de baixo (aula Editores).

Por que não deixar o servidor avisar?

Quando uma página vem pela internet, o servidor pode dizer a codificação no cabeçalho da resposta. Mas muitos não dizem. O servidor de teste do Python, que você vai usar em Servidor Local, é um deles:

$ python3 -m http.server > /dev/null 2>&1 &
[1] 127
$ curl -sI http://localhost:8000/index.html | grep -i content-type
Content-type: text/html            « diz que é HTML, mas não diz a codificação
$ kill %1

Sem charset=utf-8 no cabeçalho e sem o meta na página, o navegador tem de adivinhar. Os navegadores atuais analisam os bytes e muitas vezes acertam, mas não é garantido: quando não acertam, usam uma tabela antiga, em geral a Windows-1252 nos computadores em português. E é aí que aparece o AÃ§Ã£o. Abrindo o arquivo direto do disco (com dois cliques), também não há servidor nenhum para avisar. Por isso a regra: toda página leva o meta charset.

No editor do guia

Nos quadros "Experimente", o que você digita já chega ao navegador como texto, sem passar por bytes de um arquivo. Por isso, lá, tirar o meta charset não muda o resultado. O problema aparece com arquivos de verdade, no seu computador ou num site publicado. A seção 2 mostra o efeito real, com bytes de verdade.

Missão: a página da Ana esqueceu de dizer a codificação. Coloque <meta charset="utf-8"> como primeira linha dentro do <head>, antes do <title>.

3. Um arquivo salvo em Latin-1

Antes do UTF-8, cada região usava a sua tabela de 1 byte. No Brasil, a mais comum era a Latin-1 (o nome oficial é ISO-8859-1) e a sua prima do Windows, a Windows-1252. Nelas, o ç é um byte só, o E7. Sites e arquivos antigos ainda aparecem nessas tabelas.

Para ver o problema, a Ana fez uma cópia do index.html convertida para Latin-1, como se fosse um arquivo de 2005:

$ file index.html
index.html: HTML document, Unicode text, UTF-8 text
$ iconv -f UTF-8 -t ISO-8859-1 index.html > velho.html
$ file velho.html
velho.html: HTML document, ISO-8859 text
$ ls -l index.html velho.html
-rw-rw-r-- 1 ana ana 196 out 17 15:49 index.html
-rw-rw-r-- 1 ana ana 192 out 17 15:50 velho.html     « 4 bytes a menos: 4 letras acentuadas
file index.html
O comando file olha os bytes e adivinha o tipo do arquivo: "documento HTML, texto Unicode, texto UTF-8".
ISO-8859 text
Para o velho.html, o file reconheceu uma tabela antiga de 1 byte por letra (a família ISO-8859, da qual o Latin-1 faz parte).
196 e 192
Em UTF-8, cada letra acentuada (ã de "Pão", ç, ã, á) ocupa 2 bytes; em Latin-1, 1 byte. Quatro acentos, quatro bytes a menos.

Os bytes da linha do parágrafo, lado a lado:

$ sed -n 9p index.html | xxd
00000000: 3c70 3e41 c3a7 c3a3 6f20 72c3 a170 6964  <p>A....o r..pid
00000010: 613a 2033 3020 6d69 6e75 746f 7320 6465  a: 30 minutos de
00000020: 2066 6f72 6e6f 2e3c 2f70 3e0a             forno.</p>.
$ sed -n 9p velho.html | xxd

00000010: 3330 206d 696e 7574 6f73 2064 6520 666f  30 minutos de fo

No UTF-8, "Ação" é 41 c3a7 c3a3 6f; no Latin-1, 41 e7 e3 6f. O resto (letras sem acento, tags) é igual nas duas tabelas. O pior: o velho.html continua com <meta charset="utf-8"> lá dentro, porque o iconv converte os bytes, não o texto da página. O arquivo agora mente: diz UTF-8 e está em Latin-1. O navegador acredita no aviso e mostra P�o de queijo e A��o r�pida, como a janela 3 da seção 2.

O validador e o iconv percebem

$ vnu velho.html
"file:/home/ana/site/velho.html":8.6-8.6: error: Malformed byte sequence: “e3”.
"file:/home/ana/site/velho.html":9.5-9.5: error: Malformed byte sequence: “e7”.
"file:/home/ana/site/velho.html":9.6-9.6: error: Malformed byte sequence: “e3”.
"file:/home/ana/site/velho.html":9.10-9.10: error: Malformed byte sequence: “e1”.
$ iconv -f UTF-8 -t UTF-8 velho.html > /dev/null
iconv: sequência de entrada ilegal na posição 117
  • Malformed byte sequence: “e3” = "sequência de bytes malformada: e3". O validador lê o arquivo como UTF-8 e aponta cada byte que não faz sentido nessa embalagem, com linha e coluna: o e3 do "Pão" (linha 8) e os três acentos do parágrafo (linha 9).
  • O iconv -f UTF-8 -t UTF-8 é um truque para conferir se um arquivo é UTF-8 válido: ele "converte" de UTF-8 para UTF-8 e para no primeiro byte inválido. O > /dev/null joga fora o resultado; só interessa a mensagem. A posição 117 é o byte do ã de "Pão", contando do zero.

O conserto: converter para UTF-8

$ iconv -f ISO-8859-1 -t UTF-8 velho.html > novo.html
$ file novo.html
novo.html: HTML document, Unicode text, UTF-8 text
$ vnu --verbose novo.html
novo.html                                    « só o nome: nenhum erro

Agora a tabela de leitura (-f ISO-8859-1) é a certa, e o iconv escreve o resultado em UTF-8. O meta charset, que já dizia utf-8, volta a dizer a verdade. Se o arquivo antigo não tinha o meta, ou tinha outro valor, troque essa linha também. Nunca mande o > para o próprio arquivo de entrada (iconv … velho.html > velho.html): o terminal apaga o arquivo antes de o iconv começar a ler.

No VS Code

A codificação do arquivo aberto aparece na barra azul de baixo, à direita (por exemplo, UTF-8). Clicando nela, o editor oferece reabrir o arquivo com outra codificação (para ler um arquivo antigo do jeito certo) ou salvar com outra codificação (para convertê-lo). Para consertar um arquivo Latin-1: reabra como ISO-8859-1 (os acentos aparecem certos) e salve como UTF-8.

4. Emojis

Para o HTML, um emoji é só mais um caractere do catálogo Unicode, com 4 bytes em UTF-8. Com o meta charset="utf-8", você pode digitá-lo direto ou usar a referência numérica:

<h1>Bolo de aniversário 🎂</h1>
<p>Também com número: &#x1F382; (hexadecimal) e &#127874; (decimal).</p>

O desenho do emoji vem da fonte do sistema: o mesmo 🎂 tem uma cara no Android, outra no iPhone, outra no Windows. Um sistema antigo, sem aquele emoji na fonte, mostra um quadradinho vazio.

Emojis compostos

Muitos emojis são vários caracteres colados, que o sistema desenha como uma figura só:

<p>Cozinheira: &#x1F469;&#x200D;&#x1F373; = &#x1F469; + &#x1F373;</p>
<p>Bandeira: &#x1F1E7;&#x1F1F7; = letra B + letra R</p>
<p>Tom de pele: &#x1F44D;&#x1F3FD; = &#x1F44D; + tom médio</p>
&#x1F469;&#x200D;&#x1F373;
Mulher (👩) + um caractere invisível, o ZWJ (U+200D, zero width joiner, "juntador de largura zero") + frigideira (🍳). O ZWJ diz: "desenhe os dois como uma figura só". Se o sistema não conhece a combinação, mostra as duas figuras separadas.
&#x1F1E7;&#x1F1F7;
Bandeiras são duas "letras regionais" (B e R, de Brasil). Alguns sistemas, como o Windows, não desenham bandeiras e mostram as duas letras.
&#x1F3FD;
Um modificador de tom de pele, colado logo depois do emoji de pessoa ou de mão.

Esses emojis ocupam bem mais bytes do que parecem. A cozinheira são 3 caracteres e 11 bytes:

$ printf '👩‍🍳' | xxd
00000000: f09f 91a9 e280 8df0 9f8d b3              ...........
$ printf '👩‍🍳' | wc -c
11

f09f91a9 é a mulher (4 bytes), e2808d é o ZWJ (3 bytes) e f09f8db3 é a frigideira (4 bytes).

Emojis e acessibilidade

Leitores de tela (programas que leem a página em voz alta para quem não enxerga) falam o nome de cada emoji: "bolo de aniversário". Um título com cinco emojis vira uma frase comprida e cansativa. Use poucos, e nunca para substituir uma palavra importante: "Forno a 180 graus 🔥" é melhor que "🔥 a 180". Mais em Leitores de Tela.

Missão: coloque o emoji de bolo 🎂 no fim do título (digitado ou com &#x1F382;) e a cozinheira 👩‍🍳 no fim do parágrafo, montada com &#x1F469;&#x200D;&#x1F373;.

<h1>Bolo de aniversário</h1>
<p>Receita testada pela Ana</p>

<h1>Bolo de aniversário &#x1F382;</h1>
<p>Receita testada pela Ana &#x1F469;&#x200D;&#x1F373;</p>

Quando dá errado

Na tela: AÃ§Ã£o, Ã©, Ã£

O que significa: o arquivo está em UTF-8 (certo), mas o navegador o leu como Windows-1252. Quase sempre falta o <meta charset="utf-8">, ou ele está depois dos primeiros 1024 bytes, ou o servidor anuncia outra codificação no cabeçalho (o cabeçalho ganha do meta).

Como consertar: ponha o meta charset como primeira linha do head. Se o site está num servidor, confira o cabeçalho com curl -sI endereço | grep -i content-type: ele deve dizer charset=utf-8 ou não dizer codificação nenhuma.

Na tela: A��o, e o validador diz Malformed byte sequence

O que significa: o arquivo está salvo em Latin-1 (ou Windows-1252), mas foi lido como UTF-8. O file confirma: ISO-8859 text.

Como consertar: iconv -f ISO-8859-1 -t UTF-8 velho.html > novo.html, ou "reabrir com codificação" e "salvar com codificação" no editor. Não adianta trocar o meta para outra codificação (veja o cenário seguinte).

Declarar outra codificação: The only allowed value … is “utf-8”

A Ana tentou "consertar" o arquivo antigo trocando o aviso por <meta charset="iso-8859-1">, sem converter os bytes:

$ vnu latin1.html
"file:/home/ana/site/latin1.html":8.5-8.5: error: Malformed byte sequence: “e7”.
"file:/home/ana/site/latin1.html":8.6-8.6: error: Malformed byte sequence: “e3”.
"file:/home/ana/site/latin1.html":4.1-4.27: error: Internal encoding declaration “iso-8859-1” disagrees with the actual encoding of the document (“utf-8”).
"file:/home/ana/site/latin1.html":4.1-4.27: error: The only allowed value for the “charset” attribute for the “meta” element is “utf-8”.

O que significa: a última linha é a regra: "o único valor permitido para o atributo charset do elemento meta é utf-8". O HTML atual não aceita páginas novas em outras codificações. A terceira linha diz que a "declaração interna" (o meta) "discorda da codificação real" com que o validador leu o arquivo, e as duas primeiras são os bytes Latin-1 do "Ação", que não são UTF-8. (Um navegador obedeceria ao iso-8859-1 e mostraria os acentos certos, mas a página continua fora da regra.)

Como consertar: converta o arquivo para UTF-8 com o iconv e use <meta charset="utf-8">.

charset="utf8", sem o hífen 
$ vnu utf8.html
"file:/home/ana/site/utf8.html":4.1-4.21: error: The only allowed value for the “charset” attribute for the “meta” element is “utf-8”.

O que significa: os navegadores até entendem utf8, mas o valor oficial tem hífen. A mesma mensagem do cenário anterior, por um caractere.

Como consertar: <meta charset="utf-8">.

O meta depois de um comentário comprido: found after the first 1024 bytes

A Ana pôs no começo do head um comentário enorme, com a história do site, e o meta charset embaixo dele:

$ vnu tarde.html
"file:/home/ana/site/tarde.html":5.1-5.21: error: A “charset” attribute on a “meta” element found after the first 1024 bytes.

O que significa: "um atributo charset num elemento meta encontrado depois dos primeiros 1024 bytes". O navegador procura o aviso só no começo do arquivo; se ele vem tarde, o navegador já começou a adivinhar.

Como consertar: o meta charset é sempre a primeira linha dentro do <head>. Comentários vêm depois.

As duas formas juntas: must not include both

Páginas antigas declaravam a codificação com uma forma comprida, <meta http-equiv="Content-Type" content="text/html; charset=utf-8">. Ela ainda é válida sozinha, mas com as duas formas juntas:

$ vnu dois.html
"file:/home/ana/site/dois.html":5.1-5.67: error: A document must not include both a “meta” element with an “http-equiv” attribute whose value is “content-type”, and a “meta” element with a “charset” attribute.

O que significa: "um documento não pode ter, ao mesmo tempo, um meta com http-equiv="content-type" e um meta com charset".

Como consertar: apague a forma comprida e fique com <meta charset="utf-8">.

O iconv não converte um emoji para Latin-1 
$ iconv -f UTF-8 -t ISO-8859-1 bolo.html > bolo-velho.html
iconv: sequência de entrada ilegal na posição 126

O que significa: a tabela Latin-1 tem só 256 caracteres, e o 🎂 não está entre eles. O iconv parou no emoji (o byte 126 do bolo.html). É mais um motivo para usar UTF-8, que tem lugar para todos.

Como consertar: não converta para Latin-1. Se um sistema antigo exigir, troque o emoji por uma palavra antes.

  • Toda página leva <meta charset="utf-8"> como primeira linha do head, e o arquivo é salvo em UTF-8. O único valor aceito é utf-8, com hífen.
